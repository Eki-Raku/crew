# Crew

Use the bundled CLI at `bin/crew` relative to this plugin root, with Python 3.11+. Follow the fully quoted absolute command supplied by a hook; replace its action/arguments as needed and retain the interpreter, script, --host and --project. Bare crew examples below assume that this same plugin bin directory is on PATH. All noninteractive commands return JSON; inspect exit codes. Never start another Codex or Claude Code process to use this tool.

Codex and Claude Code keep separate homes, roles and task stores. The host is chosen by `--host codex|claude`, then `CREW_HOST`, then the detected environment, then Codex. Pass `--host` explicitly whenever the answer must be unambiguous. A role defined for one host is invisible to the other; `hosts.claude` inside a role carries Claude Code's model and effort, while the top-level fields belong to Codex. When role create omits description or instructions, it can copy those fields once from the other host in the same scope. Presets install always imports bundled templates, not the other host's custom prompt.

## First-use and onboarding

1. Read `crew preflight --project <root> --json`. If `legacy_config_detected` is true, offer `crew migrate` preview before creating new configuration. Explain conflicting Crew values are preserved and old plugins/exports require cleanup; see README.
2. Run `crew init --project <root> --json`. It persists a draft and returns `revision` and a single `step` with a question, type and choices. It does not write live roles yet.
3. Present that step in the user's language. Use the host's native question/choice tool **if available**; otherwise present numbered textual choices and wait for the user's answer. This skill cannot force a native selector to appear. Do not silently choose roles, models or effort for the user.
4. For model selection, use actual host-supported model IDs if you can read them, or ask the user to provide them. `--models-file` accepts a JSON array to seed choices. Existing configured model IDs are suggestions, not proof of availability. Effort choices are syntactically allowed values; verify support in the host picker.
5. Submit the answer via `crew init --step <returned-id> --revision <returned-revision> --answer '<JSON value>'`. Answer types: roles = array of IDs; model and effort = string. Use safe argument quoting or a subprocess argument array. Inspect the next returned step; never guess revision or stage.
6. At `confirm`, show the entire relevant preview: additions with model, effort and prompt, preserved/skipped roles and target path. Wait for explicit user confirmation. Then submit JSON true plus `--apply --confirm-token <preview-token>`. A false answer leaves the draft pending. A changed configuration invalidates the preview; reread `init` and obtain approval for materially changed details.
7. A completed wizard only saves role configuration. Preview `crew export` and apply under the user's setup authorization. On Codex, separately preview/apply `crew setup` if the user wants a global AGENTS entry; on Claude Code that command reports `not_applicable` because the SessionStart hook already carries the status. Respect enabled=false; initialization preserves that choice.

Pause safely by stopping. Run init again to resume. `--reset --apply` starts a new draft and preserves existing live configuration. Completed state persists. Use `crew init --interactive` only in a real human terminal; never open TUI inside a Hook.

## Role management

Six bundled templates: coordinator, implementer, reviewer, researcher, tester, documenter. View full prompts with `presets list` or saved `role show NAME`. Run `role spawn NAME [--count N]` to get fixed, pre-computed naming variables (`agent_type`, `task_name`, `name`, `native_nickname_candidates`) before spawning outside a workflow rather than inventing names. `presets install [names...] --model ID --effort LEVEL` imports missing templates only. For custom roles use `role create`; edit with `role update --instructions-file FILE` or `--instructions TEXT`. Omitted/empty instructions create an explicit empty_agent. Preserve an intentionally empty prompt rather than inventing a replacement. `role enable` restores saved definitions or removes inherited-role masks. `--effort` values differ per host: Codex accepts minimal/low/medium/high/xhigh, Claude Code accepts low/medium/high/xhigh/max.

Use `--lang zh|en` or CREW_LANG for interface language; template imports also accept `--prompt-lang`. Never translate stored user prompts or task state just because the interface language changes. Supported role fields are model, effort, description, instructions, max_instances (positive integer, default 1) and disabled. Unknown fields, including Claude tools, permissionMode and skills, are rejected: Crew does not implement those controls. Do not remove a requested permission restriction merely to make export succeed; keep the agent outside Crew if needed.

## Diagnostics and limits

`preflight` reports stale/missing exports for the selected host. `enabled=false` plus `needs_export` means stale project exports need removal, not permission to re-enable the project. `doctor` distinguishes static checks and model availability not live verified. `hook ping` is a simulated test, not proof a host Hook fired. Read receipts with `hook status`. A native host plugin and Hook trust must be configured in the host.

The portable manifest's extensions.com.openai is authoritative for Codex; `.claude-plugin/plugin.json` is the Claude Code manifest. Codex loads `hooks/codex.json` through its manifest; Claude Code always loads `hooks/hooks.json`. Each hook event ends with exit code 0 even on failure, because exit code 2 would block the user's prompt.

No model calls, credential collection, spending or current-controller changes are performed by Crew. Preserve LICENSE when redistributing.

## Shared task context

When a Crew hook provides task_id and version, use that task record. Without a hook, run `crew --host <host> context open --session <actual-session-identity>`; provider defaults to that host. If supplied, --provider must match --host; a mismatch is rejected before any store is opened. Pass `--task <known-id>` to share another role's task deliberately. Never invent an unrelated real host session identity, and never present another host's task ID as this host's: each host has its own store, and a task ID from the other host will not be found here. The store uses repository scope and exact provider/session association. Host hook session_id can cover a session tree/fork; it is not a verified AppServer threadId.

Read the full task state once with `context read --task ID`, and read global/project `context decisions`. Retain returned task_id/version and decision digests locally. On later turns read `context read --task ID --since LAST_SEEN_VERSION` only when version changes. Apply `changes` and `removed` to the local cache. Never advance your known version beyond a successfully read response. Refresh scoped decisions when their digest changes. A new agent starts with a full read; it cannot inherit another agent's in-memory version cursor.

After a meaningful decision, validated result, scope change, blocker, or handoff, write a concise `context patch` with expected-version and a unique request-id. State fields: summary, goal, constraints, decisions, progress, next, blockers, evidence. Use short strings/lists. Evidence should point to files/tests/commits, not copy logs. Distinguish completed and verified work from plans. Do not store secrets, transcripts or unsupported inferences. Use `checkpoint` when reorganizing a complete compact state; omit a field only when its old value is intentionally removed. CAS conflicts require rereading and merging, never blindly overwriting a newer version.

Store explicit cross-project user decisions via global decision-set; project-level durable decisions via project decision-set. A task record does not replace these scopes. Do not promote a temporary preference to a global rule without the user's direction.

If task_id changes or the hook reports reset, discard the old shared-task cache. A manually deleted task must not be reconstructed from the earlier transcript or old checkpoint. Work from the current request and newly established facts, asking for necessary missing information. Stale writes to the old ID are rejected. Explicit user-requested restore may recover an old record, but must not silently relink an active replacement session.

This release does not detect host archive/delete events or automatically clean up lifecycle records. Manual archive/delete/restore and session-state are available in CLI/TUI. SessionEnd/unknown does not mean deletion. A local tool cannot retract text already inside a model conversation or guarantee the model writes a checkpoint; follow this protocol when working with Crew.

## Engineering workflow (Codex)

For engineering work, use the persisted workflow to keep implementation and independent review assigned across turns. Ordinary questions do not start a workflow. SessionStart supplies the real session ID and an absolute start command. Custom role IDs can replace the default `implementer`/`reviewer`; preserve their selected models and prompts.

1. Start once: `crew workflow start --session ID --goal '...' --acceptance '...' --implementer ROLE --reviewer ROLE`. This associates the existing shared-context task. Save `task_id` and workflow `version` (separate from the shared-context version).
2. `workflow dispatch --task ID --expected-version N [--count K]` prepares a stage and returns `dispatch_input` (and `dispatch_inputs` when `K > 1`, up to the role's configured `max_instances`, default `1`). Pass `agent_type`, `task_name` and `message` to the host's native `spawn_agent` exactly as returned: the dispatch fixed these names once, and the PreToolUse hook blocks any spawn of a workflow role that differs, omits the marker, or invents its own `task_name`. Never spawn `crew_*` roles of an active workflow without running `workflow dispatch` first. Append relevant context and distinct non-overlapping subtask scopes after the message, preserving the leading dispatch marker. The role name comes from the host exporter. Use `dispatch_input.name` (or `preflight.subagent_names`, formatted as `【model】role` or `【model】role#i` when parallel, with localized built-in role names per active language and `role_id` for custom roles) as the canonical display name when naming or reporting dispatched subagents while keeping `agent_type` unchanged. Never launch another Codex process.
3. Read `workflow read --task ID` after the worker returns. Hooks bind the successful spawn call and agent ID, then record Start/Stop. Stop alone does not accept the work. For implementation, record `workflow deliver --task ID --expected-version N --files PATH... --summary '...' --tests '...'`. List every modified/deleted artifact in scope. The store fingerprints the declared paths; review checks their exact content.
4. Dispatch the review stage with its returned packet, including goal, acceptance, artifacts and test evidence. The reviewer must be a different actual agent from every implementer in this workflow. After it returns, record `workflow review --task ID --expected-version N --verdict pass|changes --summary '...'`. Changes return to implementation, with review feedback in the next packet.
5. Complete with `workflow finish --task ID --expected-version N`. Modified artifact content invalidates review. Use `retry --reason '...'` to rebuild; after a completed/cancelled cycle use `next --goal '...' --acceptance '...'` for the next task in the same session.

Every mutation requires the version returned by the latest read. Resume/compaction restores the existing task and assignment; do not create duplicate agents. A failed dispatch can be retried explicitly with a fresh marker. This release uses fresh native subagents per assignment; reuse of an existing agent requires a future adapter with explicit send-message correlation. Wait for/cancel any outstanding old agent before retrying, so it cannot edit concurrently. Pause with `workflow pause --reason '...'` for approval or external blockers; `resume` continues the same stage. `cancel --reason '...'` records cancellation. These commands record state, not a native agent termination.

Codex PreToolUse gates the supported `apply_patch` path. New workflows default to `--edit-policy identity`: edits require the current live implementer agent_id and exported agent_type. If default implementation/review roles exist and no workflow has started, the hook supplies a start command and denies that edit. Custom-role users start explicitly. Newer Codex source provides optional child-agent identity fields. A missing identity is unverified, not proof of a coordinator: identity mode denies that edit with a capability diagnostic. For an older client, explicitly select `--edit-policy stage` at start or on a new cycle after cancelling the old cycle. It checks stages and still rejects explicitly mismatched worker identities; missing identities fall back to stage checks. This compatibility policy is shown in `edit_protection`. Previously stored development workflows without a policy keep stage behavior. Do not change modes silently or reroute a denied edit through shell/MCP. Shell/MCP writes are outside this edit gate. Stop returns one bounded correction for unchanged unfinished state; paused/cancelled work and repeated correction are released. Missing hooks leave observations missing and completion unavailable. Hook trust, event support and real host enforcement require client validation; `hook ping` remains a simulation.

The CLI and TUI use the same state machine in the existing context database. No transcript scan, extra model judge, token-share target, scheduler or service is introduced. Use `--lang zh|en` for built-in guidance. Existing custom role prompts remain unchanged; the bundled coordinator template now describes this flow for new imports.

### Task-owned resources and handoff reports

After creating a QA process, tab, app or temporary artifact, register it with `workflow resource-add --task ID --expected-version N --kind process|tab|app|temporary|other --locator 'original handle' --owner AGENT_ID --purpose '...' --creation-evidence '...'`. Use the actual observed agent ID or coordinating session. Record only task-created resources; a terminal handle is not an OS PID and an occupied port does not prove ownership.

Use the original host tool to close your resource, verify the result, then `resource-release --resource-id ID --evidence '...'`. For user-requested retention, use `resource-retain` with the user's instruction as evidence. Respect the original permissions for every cleanup action. The plugin records evidence and does not execute cleanup. Review pass, finish and the next cycle reject open resources; cancellation preserves them so cleanup can still be recorded. The review packet includes resources to inspect. Unlisted resources require an ownership/cleanup check, not an invented clean result.

For approval/external blockers, `pause --reason '...'`. Resume only after a definite result with `resume --reason 'the actual result/authority'`. An unrelated successful tool call is not approval of an earlier pending call. Pause state suppresses Stop corrections.

Use `workflow report --task ID` for concise handoffs. Distinguish observed native dispatch identities from configured model defaults and agent-reported tests, cleanup and review. Existing custom prompts are not overwritten.

Resource registration is explicit. After cancellation, you may still record a late-discovered existing task-owned resource. `next` resets the current-cycle report, including disposed/retained resource entries; preserve durable handoff facts in shared context/project documents first. Store brief evidence pointers, never credentials, full token-bearing URLs or sensitive logs in locators, creation evidence, tests or cleanup fields; these may be shared in the review packet.
